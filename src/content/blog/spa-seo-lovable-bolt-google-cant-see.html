You built an app with Lovable or Bolt, put it online, and Google barely shows it. Search for your own pages and nothing comes up. Ask ChatGPT about your product and it has never heard of it. The cause is often not your content. It is how the page is delivered. Facts about Google, Lovable, Netlify and React Router come from their own docs, checked in November 2026.

Short answer: many AI-built apps are single-page apps: the browser builds the page with JavaScript, so the first HTML a crawler gets is almost empty. Google can usually run the JavaScript, later. Many other crawlers can't, and you can't count on them. Check what a crawler really receives (10 minutes, below). If it is empty, give each public page its own title, description and canonical, and build those pages as real HTML at build time.

1. Why it happens

A single-page app (SPA) sends one small HTML file: a root div and some script tags. The scripts then draw the page in the visitor's browser. Lovable's SEO docs mention "older React + Vite apps". I did not find a Bolt doc page that says how Bolt apps are built, so open your own package.json and see whether it lists React and Vite.

Google's JavaScript SEO basics say: "Google processes JavaScript web apps in three main phases:" crawling, rendering and indexing. The page also says Googlebot "queues all pages with a 200 HTTP status code for rendering", and a page may wait in that queue. So Google can see your JavaScript content, but later and with extra steps. The same page adds that server-side or pre-rendering "is still a great idea", because it also helps crawlers that can't run JavaScript.

That matters for AI search. In December 2024, Vercel and MERJ published a study of AI crawlers. It says: "The results consistently show that none of the major AI crawlers currently render JavaScript." It is one study, almost two years old, so it is not a permanent fact. It is still reason enough not to count on AI crawlers running your scripts. More on AI search: getting recommended by ChatGPT.

2. A twist: what Lovable does for you

Lovable's SEO docs say new apps created from May 13, 2026 (June 22, 2026 on Enterprise plans) "use TanStack Start with server-side rendering (SSR)", and that "Every request returns fully rendered HTML, for humans and crawlers."

For older React + Vite apps, the docs say Lovable uses "on-request pre-rendering on deployed public URLs", and that "Pre-rendering is only served to verified crawlers." Unverified bots "see the regular single-page app". The docs also say: "Content that loads late may be missing." The docs I read only cover apps hosted by Lovable. They say nothing about an app you moved elsewhere. If you moved it (see moving your app to your own GitHub and hosting), I can't promise that the pre-rendering comes with it, so test your own site.

3. Typical symptoms

  • Every page has the same title and description. Lovable's docs list "Duplicate titles, placeholder text, weak descriptions, or wrong canonical URLs" among the things its review checks.
  • The canonical tag points to the home page on every URL. Search Console may show Duplicate, Google chose different canonical than user. Google's page indexing report help describes it as: "This page is marked as canonical for a set of pages, but Google thinks another URL makes a better canonical."
  • Pages the crawler saw but did not index. The same help page lists Crawled - currently not indexed: "The page was crawled by Google but not indexed." It adds that this is "a common message for many sites", so it has many possible causes. An empty or duplicate page is one of them.
  • Made-up URLs return 200. Netlify's rewrite docs show the usual SPA rule /* /index.html 200 and say it will "serve the index.html instead of giving a 404 no matter what URL the browser requests". Search Console may then report Soft 404: "The page request returns what we think is a soft 404 response."
  • Blog or product pages are missing from sitemap.xml, or the sitemap does not exist. Lovable's docs say it "creates a robots.txt with every new project, but not always a sitemap".
  • A list page that says "Loading..." in the HTML, because the list is fetched by JavaScript after the page loads.

4. How to check in 10 minutes

  1. View source, not Inspect. In Chrome, right-click and choose View page source. This is the HTML as delivered. Inspect shows the page after JavaScript has run. If your headline and text are in Inspect but not in View source, a crawler that skips JavaScript sees an empty page.
  2. Use curl. Run curl -s https://yoursite.com/some-page | grep "a phrase from the page". No output means the text is not in the HTML. Also look at the <title> and canonical lines in the result.
  3. Search Console, URL Inspection. Per Google's URL Inspection help, click Test live URL, then View tested page. You see "the raw HTML returned", and a Screenshot tab. A passing test does not promise indexing.
  4. Open /sitemap.xml and /robots.txt. Is every public page in the sitemap? Does robots.txt have a Sitemap: line? Google's robots.txt intro says it is used "primarily to manage crawler traffic" and is "not a mechanism for keeping a web page out of Google", so check that it does not block pages you want found.
  5. Open a made-up URL, like /this-page-does-not-exist. It should say not found, and the status should be 404. Use curl -I to see the status.

5. Fixes, in order of value

a) Give each public page its own title, description and canonical. Google's JavaScript guide says "You can use JavaScript to set or change the meta description as well as the <title> element" and "You can use JavaScript to set the canonical URL". Libraries like react-helmet-async or Unhead do this. But on its own this only helps crawlers that run JavaScript. The tags are still set after the page loads. The guide also says the best way to set the canonical is HTML, and a JavaScript value should match the HTML one.

b) Build the public pages as real HTML at build time (prerendering). Every public route becomes its own HTML file with the text in it. With React Router, the pre-rendering docs say: "Pre-rendering is enabled via the prerender config in react-router.config.ts." That page is for framework mode only, so a plain Vite app that uses React Router as a library can't use it as is. The docs also say the value true "will not include any dynamic paths (i.e., /blog/:slug) because the parameter values are unknown", so for blog posts you pass the list of paths. The other routes are a static site generator for the public pages, or a framework that renders on the server. Which one fits depends on your app. The fix or rebuild post helps you judge it.

c) A complete sitemap.xml and a robots.txt that points to it. Google's sitemap overview says a sitemap "helps search engines discover URLs on your site, but it doesn't guarantee that all the items in your sitemap will be crawled and indexed". List every public page, with full URLs on your own domain.

d) Real 404s for unknown URLs. Google's JavaScript guide has a section called "Avoid soft 404 errors in single-page apps". It gives two options: a JavaScript redirect to a URL that returns a 404, or a noindex robots meta tag on error pages. If your host rewrites everything to index.html, a prerendered site fixes most of this, because real pages are real files and the rest can fall through to a 404 page.

e) Skip dynamic rendering. That means serving crawlers a different, pre-built version than users get. Google's dynamic rendering page says: "Dynamic rendering is a workaround and not a recommended solution". Prefer fix (b).

The part of your app behind a login does not need any of this. It does not need to rank. Leave it as it is.

What I did on my own sites

These are my apps, checked in the code in November 2026. I have no traffic numbers to show for them yet.

  • TuneCraft (tunecraft.music): the landing page used to be an empty app shell for crawlers that don't run JavaScript. It is now prerendered at build time, so about 250 words of real text are in the HTML. Its Privacy and Terms pages got the same fix.
  • WuXing Zodiac (wuxingzodiac.me): its 5 blog posts were invisible to search. Each post URL served the home page with a canonical to the home page, the posts were not in the sitemap, and /blog said "Loading posts...". Now /blog and every post are built as static pages with their own title, description and canonical, and they are in the sitemap.
  • dizid.com itself is prerendered at build time (vite-ssg), so every page and post is real HTML.

How to ask your AI tool, or a developer

"Improve my SEO" is too vague. Name the pages, the tags and what must stay the same. Two examples:

  • "Give each public page its own title (under 60 characters), meta description (under 155 characters) and canonical URL on https://yoursite.com, for /, /pricing, /about and each blog post. Do not change anything behind the login. Do not change the design."
  • "Build the public pages /, /pricing, /about, /privacy, /terms and /blog/* as static HTML at build time, so the text is in the HTML file without running JavaScript. Generate sitemap.xml with all of them, and make unknown URLs return a real 404. Keep the logged-in app working as a normal single-page app. Tell me what you changed."

The second prompt is a bigger change. Try it on a copy of your project first, and use curl from step 4 to see if it worked. If each prompt breaks something else, start with the first tests worth writing.

Checklist

  1. View source shows your real headline and text, not an empty root div.
  2. Each public page has its own title, description and canonical.
  3. The canonical points to the page itself, not to the home page.
  4. sitemap.xml lists every public page, and robots.txt points to it and does not block them.
  5. A made-up URL returns a real 404.
  6. List pages (blog, products) have their items in the HTML, not "Loading...".
  7. Search Console URL Inspection, live test, shows your text in the tested page.
  8. The logged-in part of the app still works.

Before a launch, also go through the launch-ready checklist. Slow pages hurt too: see why your AI-built app is slow.
