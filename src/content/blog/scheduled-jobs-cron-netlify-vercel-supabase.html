Your app sends a daily digest, deletes old records, syncs data or sends reminders. Then one day you notice it stopped, and nothing told you. A scheduled job that does not run makes no error. Here is where such jobs can run, what each platform documents today, and how to make them safe. Limits change, so open the linked page before you rely on a number.

Short answer: use a schedule only for work that is driven by time. Pick the scheduler on the platform where your code and secrets already live. Make every run safe to repeat, keep each run short, and add a heartbeat check so you hear about a missed run.

1. Schedule or event?

A schedule fits work with no trigger except the clock:

  • A daily or weekly digest email.
  • Deleting old records, such as unconfirmed accounts.
  • Syncing data from a service that cannot call you.
  • Renewing something that expires, like a token.

Use an event or a webhook when something happens that you can react to: a payment, a sign-up, a file upload. Do not poll every minute for "did a payment arrive?" when the payment provider can call you.

2. What each platform documents

Netlify Scheduled Functions

The Netlify docs say:

  • You use cron syntax, and it runs in UTC. For example, 0 0 * * * is midnight UTC. Shortcuts like @hourly and @daily work too.
  • A scheduled function has a 30 second execution limit. For longer work, Netlify points you to background functions.
  • It runs on a schedule only for published deploys. Deploy previews and branch deploys do not trigger it.

Vercel Cron Jobs

Vercel's usage and pricing page lists 100 cron jobs per project on every plan. On Hobby, a job can run once per day at most, and an expression that runs more often fails the deployment. Hobby timing is loose: a job set for 1:00 can run any time between 1:00 and 1:59. Pro allows once per minute with per-minute precision.

The management page adds several points:

  • Cron jobs run only on production deployments.
  • Vercel does not retry a failed cron job.
  • Delivery is best effort. A run can be missed with no log entry, and the same run can occasionally be sent twice.
  • If a run is longer than the interval, a second one can start while the first is still going.

Vercel calls Cron Jobs a legacy feature and is moving to Schedules, which are in beta with different limits. Check which one you use.

Supabase Cron

Supabase Cron is a Postgres module built on pg_cron. A job can run SQL, call a database function or make an HTTP request, such as to an Edge Function. The docs recommend no more than 8 jobs running at once, and each job no longer than 10 minutes. Run history is in the cron.job_run_details table, and the quickstart warns that those records are not cleaned up automatically. Check the time zone your jobs use in the docs before you rely on a local time. Why dates go a day off in the app itself: see dates and time zones.

To call an Edge Function, the scheduling guide combines pg_cron with pg_net. It says to keep the project URL and secret key in Supabase Vault, and not to use the publishable key, because anyone can read it.

GitHub Actions

The GitHub docs say a schedule can be delayed during periods of high load, that the shortest interval is once every 5 minutes, and that it runs only on the default branch. In a public repository, scheduled workflows are disabled when there has been no repository activity for 60 days. The workflow syntax page says the default time zone is UTC, and that a timezone key accepts an IANA time zone name.

3. Time zones and daylight saving

Netlify's docs say UTC. GitHub's say UTC by default. For Vercel Cron Jobs and Supabase, I did not find a time zone statement on the pages I read, so check before you assume.

UTC does not change with the seasons, but your users' clocks do. A job set for 07:00 UTC runs at 08:00 in Amsterdam in winter and 09:00 in summer. If "9:00 local" matters, either set a time zone where the platform supports it (GitHub does), or run the job every hour and let your code check whether it is 9:00 for that user now.

4. Overlaps, retries and safe repeats

Treat every job as one that can run twice, or not at all. Vercel says this about its own delivery. For any platform, three habits help:

  • Make it idempotent. Running twice must give the same result as running once. "Set status to sent" is safe. "Add 10 credits" is not. More on this in duplicate records from double clicks and retries.
  • Record what you did. Mark each digest or reminder as sent, and query for all work not yet done. Then the next run catches up after a missed one.
  • Use a lock. If a run can take longer than the interval, let the job exit when another run is active. Vercel suggests a lock for this.

5. Time limits: split long jobs

Netlify gives a scheduled function 30 seconds. Supabase recommends 10 minutes per job. A large sync will not fit. Process a batch, save where you stopped, and let the next run continue.

6. Failures are silent

When a job does not run, there is no error to see. The schedule may be off, the deploy may not be published, the repository may be inactive, or the platform may skip a run. Two habits help:

  • Log every run. Write one line at the start and one at the end, with the number of items handled. For pg_cron, read cron.job_run_details, and clean it up yourself.
  • Add a heartbeat. At the end of each successful run, request a URL from a check service. If it is not requested on time, you get an alert. This catches a job that never started, which an error alert cannot. I describe the setup in uptime checks and error alerts for small apps.

7. Secrets live where the job runs

A job runs on a platform, so it needs the secrets there: the database URL, email key and so on. On Netlify, a variable must include the Functions scope, variables set in netlify.toml are not available to functions, and a new value applies only after a new deploy, as the environment variable docs explain. On Vercel, a CRON_SECRET variable is sent as an Authorization header, so your endpoint can reject callers that are not Vercel. For Supabase, use Vault as above. If your emails come from the job, also read SPF, DKIM and DMARC for app emails.

8. Pick a platform

  • Your app is already on Netlify and the job is short: a Scheduled Function. Keep it under 30 seconds, or start a background function.
  • Your app is on Vercel: Cron Jobs. On Hobby, the job can run once a day and at a loose time. Move to Pro or accept that.
  • The work is mostly SQL on your Supabase data: Supabase Cron. For code, call an Edge Function.
  • Longer jobs, or your host has no scheduler: a GitHub Actions schedule. Time precision is loose, and public repos pause after 60 days without activity.

What I do

On my job board, Remote Job Radar, the daily ingest and the digest email run from a GitHub Actions schedule, at 03:13 UTC. When a run fails, it sends a push message to my phone through ntfy. That covers failures. A run that never starts sends nothing, so a heartbeat check is the part to add. My own site, dizid.com, has no scheduled jobs.

Checklist

  1. Is a schedule the right trigger, or should an event start this?
  2. Does the platform's documented limit fit the frequency and run time you need?
  3. Is the time in UTC, and does daylight saving matter to your users?
  4. Is it safe to run twice, and safe to skip one run?
  5. Does it work in batches that fit the time limit?
  6. Does it log the start, the end and the count?
  7. Does a heartbeat alert you when it does not run?
  8. Are all secrets set on the platform where the job runs?
  9. Does it run on the deploy that counts: published, production or default branch? If you moved hosts, see moving your app to your own GitHub and hosting.
