Your app shows an order list, a chat, a dashboard or a booking calendar. Someone else changes something, and your screen stays the same until you reload. Or you fixed that with "realtime", and now the bill jumps, the connection drops on phones, or a user sees rows that are not theirs. Apps built with Lovable, Bolt, Cursor and Replit hit this often. Vendor facts below come from each vendor's own docs, checked in November 2026.

Short answer: most small apps do not need realtime everywhere. Use it for the one screen that really needs it, keep it behind the same access rules as the rest of your data, and know what it costs. For everything else, refresh after an action or poll slowly.

Three ways to get fresh data

  • Refresh on an action. Fetch again after the user saves, clicks refresh or opens the page. Enough when only the user changes the data, or others change it rarely.
  • Polling. Ask the server every N seconds. Enough when a delay of 10 to 60 seconds is fine, like an admin order list or a dashboard.
  • Realtime subscription. The server pushes changes over an open connection. Worth it when people wait for each other and a delay feels broken, like chat or a shared board.

Polling is boring and works everywhere. Realtime feels better but adds open connections, more rules to secure and sometimes a metered bill. Pick the cheapest way that does not annoy your users.

Supabase Realtime

The Realtime overview lists three features. Postgres Changes: "Listen to database changes in real-time." Broadcast: "Send low-latency messages between clients." Presence: "Track and synchronize user state across clients." Presence is for things like who is online.

Postgres Changes and your access rules

The Postgres Changes guide says: "Postgres Changes authorizes every event against each subscriber." So your Row Level Security policies apply. Two details matter:

  • You must switch the table on. The guide says: "Go to your project's Publications settings, and under supabase_realtime, toggle on the tables you want to listen to."
  • Deletes are the exception. The guide warns: "RLS policies are not applied to DELETE statements," because "there is no way for Postgres to verify that a user has access to a deleted record."

If you do not have RLS basics yet, start with database security checks for AI-built apps. The Realtime authorization page adds that for Broadcast and Presence you control access with "Row Level Security policies to the realtime.messages table", and that to enforce private channels "you need to disable the 'Allow public access' setting in Realtime Settings."

Cost of authorization, and scale

The Postgres Changes guide explains that "throughput scales with the number of subscribers, not the write rate." It also says: "If you expect more than ~3,000 concurrent subscribers on the same changes, use Broadcast to stream database changes instead." For a small app this is rarely your first problem. It is worth knowing before a launch, see the launch day traffic spike.

Limits per plan

The Realtime limits page lists quotas per plan. At the time I checked, the Free plan allowed 200 concurrent connections and 100 messages per second, and the Pro plan 500 concurrent connections and 500 messages per second. The same table has limits for channel joins, Presence and payload sizes. Check the page for your plan before you rely on a number.

Firestore real-time listeners

In Firestore you attach a listener with onSnapshot. The listen to real-time updates page says: "An initial call using the callback you provide creates a document snapshot immediately", and "each time the contents change, another call updates the document snapshot." Listeners start from the local cache: "Cloud Firestore snapshot listeners take an initial snapshot from the local cache."

You must stop them yourself: "you must detach your listener so that your event callbacks stop getting called." In the web examples, onSnapshot returns a function. Call it when the screen goes away.

How listeners are billed

The Firestore pricing page says you are charged "a read each time a document in the result set is added or updated", and also when "a document is removed from the result set because the document has changed". Deleted documents are not charged as reads. The page's reconnect rule depends on offline persistence. With persistence enabled, if the listener is disconnected "for more than 30 minutes", you are charged "as if you had issued a brand-new query." With persistence disabled, you are charged as a new query whenever the listener disconnects and reconnects. So a phone that goes in and out of coverage can cost more reads than you expect. A listener on a big collection can re-read all of it. For the bill side, see avoiding a surprise bill.

Security rules and limits

The rules and queries page says "security rules are not filters" and that "If a query could potentially return documents that the client does not have permission to read, the entire request fails." That page does not mention listeners by name. The listen page only says that a listen "may occasionally fail", for example "due to security permissions", and then the listener gets no more events. So build your query to match your rules, and show an error if it fails. I did not find listener limits on the quotas page, so I do not state any.

Neon and plain Postgres apps

If your app talks to Postgres without a realtime service, you have two simple options. Poll an endpoint every 10 to 30 seconds, only on the screen that needs it. Or add a hosted realtime or pub-sub service and send an event when a row changes. The second is more work and adds a vendor, so I would start with polling and move only if polling is not good enough. Whatever you pick, the endpoint must check who is asking, as for every other read.

Phones and flaky networks

A phone sleeps the tab, switches from wifi to mobile data, or goes through a tunnel. The connection drops and the screen can silently go stale. Two habits fix most of it:

  • Refetch when the tab comes back. MDN's Page Visibility API page says the API provides "events you can watch for to know when a document becomes visible or hidden." Listen for visibilitychange, and when the page is visible again, reload the data and check the subscription is alive.
  • Show a "reconnecting" state. A small banner like "Reconnecting, data may be old" is better than a screen that looks live but is not. When the connection returns, refetch, then show the data.

Test it by turning airplane mode on and off with the app open. More on phone problems in the phone fixes post.

Common mistakes in AI-built apps

  • Subscribing in a component that mounts many times. Each mount opens a new subscription and the old one never closes. Unsubscribe when the component unmounts: removeChannel in Supabase, which per the reference "Unsubscribes, removes and tears down a single channel", or the function returned by onSnapshot in Firestore.
  • Subscribing to a whole table. Use a filter for one room, one user or one order. The Postgres Changes guide says to "Use the filter parameter for granular changes".
  • Trusting messages without access rules. A realtime channel is another way to read your data. Secure it as you secure the database.
  • Polling every second for every visitor. One hundred visitors is one hundred requests a second. Poll slower, and stop polling when the tab is hidden.

Prompts for your AI tool

  • "List every place this app subscribes to realtime updates or polls. For each, show the file, the table or collection, whether there is a filter, and whether it unsubscribes when the component unmounts."
  • "On the orders page only, subscribe to changes for the current user's orders, with a filter on user_id. Unsubscribe on unmount. Don't add realtime to other pages."
  • "When the browser tab becomes visible again, or the connection comes back, refetch the data and resubscribe. Show a 'Reconnecting' banner while the connection is down."
  • "Replace this realtime subscription with polling every 30 seconds, paused while the tab is hidden. Keep the same loading and error states."

Ask for one change per prompt and test it with two browsers, one logged in as each user.

Checklist

  1. Each screen uses the cheapest way that works: refresh, polling or realtime.
  2. Realtime is only on screens where a delay feels broken.
  3. Row Level Security or security rules are on, and tested with two users.
  4. Subscriptions use a filter and do not cover a whole table.
  5. Every subscription is closed on unmount. No duplicates after navigating around.
  6. The app refetches when the tab becomes visible and after a reconnect.
  7. A "reconnecting" state shows when the connection is down.
  8. Polling is slow and stops when the tab is hidden.
  9. You checked your plan's limits and what listener reads cost on the vendor's page.
  10. Deletes do not leak: you tested what other users receive.
