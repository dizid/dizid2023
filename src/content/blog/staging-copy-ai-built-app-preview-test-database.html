You ask Lovable, Bolt or Cursor for a change, it looks fine in the editor, and you publish. Now the change runs on your real users and your real data. If it breaks something, they find out first. A staging copy is a second version of your app where changes land first. Vendor facts below come from each vendor's own docs, checked in November 2026.

Short answer: give every change a preview URL, point that preview at a separate test database, and give it test keys for payments and email. Keep live keys only in production. The danger is a preview that quietly uses your live database or live Stripe key. If a bad change already went live, see how to roll back a broken deploy. This post is about not needing that.

1. A preview URL for the code

A preview deploy is a copy of your site at its own address, built from a branch or pull request. Your live site does not change.

Netlify. The Deploy Previews page says Netlify builds a Deploy Preview by default when you open a pull or merge request in a connected repository. For pull request #42 the address looks like "deploy-preview-42--mysitename.netlify.app". The docs add that the base branch must be a production branch, or a branch that has branch deploys enabled.

Vercel. The Environments page says Vercel creates a preview deployment by default when you push a commit to a branch that is not your production branch, or create a pull request. Each deployment gets its own URL: a branch URL for the latest changes on that branch, and a commit URL for that exact deployment. New projects start with Vercel Authentication unless your team set a different default, so visitors to a preview must log in with a Vercel account that has access to the project. To show a preview to someone else, the docs say to approve their access request or send a Shareable Link.

Lovable and Bolt. Lovable's publish page says "The live site keeps showing the version you published, and later changes stay off it until you publish again." Bolt's publish page says "After you publish, changes you make to your Bolt project aren't automatically applied to your published site." So in both tools the editor is a place to try things, and publishing is a separate step.

Netlify and Vercel previews need your code in GitHub with your own hosting. See moving a Lovable or Bolt app to your own GitHub and hosting.

2. A separate database for testing

This is the part people skip. A preview deploy of the code is worthless as a safety net if it reads and writes your live database. A test that deletes rows deletes real rows.

  • A second Supabase project. The simplest one: own URL, own keys, own tables. Copy the table structure over and add a few fake rows.
  • Supabase branching. Supabase's branching page says "Each branch is a separate environment with its own Supabase instance and API credentials." It also says "By default, new branches do not start with any data or storage objects from your base project." So a branch starts empty. You add test data with a seed file or the "Include data" option. That page does not say which plans include branching, so check Supabase's pricing page before you plan around it.
  • Neon branches. Neon's branching page says "A branch is a copy-on-write clone of your data." Branches are created with all of the data that existed in the parent branch by default. That is handy, but it puts real customer data in your test copy. Think about who can see it.
  • Firebase. Firebase's environments page says "Firebase recommends using a separate Firebase project for each environment in your development workflow." For local work, the Emulator Suite lets you connect your app to emulators for testing "without touching production data."

Whichever you pick, never run a destructive test on live data. And know how to restore a backup before you need one.

3. Environment variables per context

Your app reads its database address and its keys from environment variables. Both hosts let you set a different value for each kind of deploy.

Netlify. The environment variables page says environment variables have one value for all deploy contexts by default, but you can set a different value for each context: Production, Deploy Previews and Branch deploys. You can also set a value for one branch, such as staging.

Vercel. The environment variables page lets you choose the environments a variable applies to: Production, Preview, Development, or a custom environment. Its Environments page answers the key question: "Do preview deployments use production environment variables?" with "No. Preview deployments use the variables you scope to the Preview environment." One exception: the first deployment of a new project is always a production deployment, so it builds with your Production variables.

Two things to know:

  • Changes need a new deploy. Vercel says changes to environment variables apply only to new deployments, not to previous ones. Redeploy after you change a value, and check Netlify's docs for how your site picks up changes.
  • Vercel custom environments. A named staging environment needs a Pro or Enterprise plan. The same page shows another way that works on all plans, Hobby included: a Git branch called staging with its own domain and its own Preview variables.

The setup to aim for: live database address and live keys only in Production. Test database address and test keys in Preview or Deploy Previews. If a variable is missing in preview, never copy the live value over. For keys that must stay secret, see the API key check.

4. Payments in staging

Stripe calls its testing environment a sandbox. The testing page says sandboxes "allow you to test your integration without making actual charges or payments." In a sandbox you use test API keys and test card numbers, and the page says test card numbers "are only valid in sandboxes. Don't use them for real payments."

Stripe also says objects in one mode are not reachable from the other: "API objects in one mode aren't accessible to the other." And: "Your test and live mode API keys affect the behavior of your code." So whether a preview takes real money depends on which key it holds, not on which Stripe screen you looked at. Put test keys in Preview, live keys in Production only.

Webhooks need the same care. Stripe's webhooks page says "Stripe generates a unique secret key for each endpoint. If you use the same endpoint for both test and live API keys, the secret is different for each one." So the preview needs its own webhook endpoint and its own signing secret (it starts with whsec_). A live signing secret in a preview makes every test webhook fail verification. For the full payment checks, read payments in an AI-built app.

One warning from the same page: Stripe's older test mode sandbox shares some settings with live mode. For new integrations it recommends a general sandbox. Check which one you are in before you change settings.

5. Emails from staging

A test that signs up fifty fake users must not email real addresses. Two rules:

  • Use only addresses you own. Test with your own inbox or a throwaway test inbox. Never load a copy of the live customer list into the test database.
  • Use a different sender setup in preview. A test key from your email provider, or a switch in the code that sends everything to one inbox.

Two facts I could confirm. Stripe's testing page says it does not email customers from sandboxes by default. And Supabase's custom SMTP page says its default email service "will refuse to deliver messages to addresses that are not part of the project's team," with a limit of 2 messages per hour that "can change without notice." So the default sender won't email strangers during tests, but it is too limited to test many sign-ups. For real sending, see why app emails land in spam.

6. Sign-in on preview URLs

Sign-in often works on your live domain and fails on a preview. The reason: login providers only send people back to addresses on an allow list, and the preview address is not on it.

Supabase's redirect URLs page says "Supabase allows you to specify wildcards when adding redirect URLs to the allow list." It suggests https://**--my_org.netlify.app/** for Netlify deploy previews and https://*-<team-or-account-slug>.vercel.app/** for Vercel, and says to set the Site URL to your official site URL. The Site URL is the default redirect, so keep it on your live address.

If you use Google or Apple sign-in, they have their own rules about which addresses are allowed. What breaks with social sign-in covers that. Put the preview wildcards in your test project, not your live one.

7. A simple routine

  1. Branch. Make the change on a branch, not on the main branch.
  2. Preview. Open a pull request. Wait for the preview URL.
  3. Check it points at test. Check the network tab for the database host. If the live database shows up, stop.
  4. Click the key flows. Sign up, sign in, the main action, a test payment with a Stripe test card, the email in your own inbox. The first tests worth writing turn these into automatic checks.
  5. Merge. The live site deploys.
  6. Smoke check live. Sign in, do the main thing once. Keep the rollback page open in another tab.

Package updates go through the same routine. GitHub security alerts: what to fix first shows which ones to do first.

Example prompts for your AI tool, adapted to your stack:

  • "Read the database URL and the Stripe key from environment variables only. List every place the app reads a key."
  • "I have a separate test Supabase project. Make previews use its URL and anon key through environment variables. Never use the live project's keys in code that runs on previews."

Set the real values yourself in your host's settings. Never paste live keys into an AI chat.

8. Checklist

  • Every change goes through a branch and a preview URL.
  • Previews use a test database, never the live one.
  • Live keys exist only in Production. Previews hold test keys.
  • Stripe test keys and a separate test webhook with its own signing secret in previews.
  • No real customer addresses in the test database. Test emails go to inboxes you own.
  • Preview URLs are on the sign-in redirect allow list of the test project.
  • After changing an environment variable, redeploy.
  • After merging, one smoke check on the live site.
