The app is 80% done. It looks right, the demo works, and then every new prompt breaks something that worked yesterday. You fix the login, the checkout stops. You fix the checkout, and the dashboard shows the wrong data. Sooner or later the question comes up: can this be fixed, or do I start over?

It's a common question with apps built in Lovable, Bolt, Cursor or v0. The short answer: a full rebuild is rarely the right first move, but "one more prompt" usually isn't either. Below is how to tell the difference, and a self-check you can do in 30 minutes before you pay anyone for either.

First: get the code out of the builder

You can't judge an app you can only see through a chat window. Before anything else, put the code somewhere you control. Lovable's GitHub integration lets you "export and two-way sync" your project code with GitHub, and the docs say it's "available on all plans". Bolt and v0 also let you connect GitHub or download the code.

Once the code is in your own GitHub account, three things change. You own a copy. A developer can read it without logging in to your builder account. And every change from then on has a history you can roll back.

Why "one more prompt" keeps making it worse

An AI builder changes the files it thinks matter for your last message. It doesn't always take the whole app into account, so a fix in one place can quietly break another. Each round adds a little more code on top: a second version of a component, a workaround for the last workaround. After enough rounds the app has three ways of doing the same thing, and nobody knows which one is used.

So the first step is the same whether you fix or rebuild: stop adding features for a few days and take stock.

Signs your app can be fixed

  • The data makes sense. You can describe every table in one sentence ("users", "orders", "bookings"), and the tables match how your business works.
  • Sign-in and payments use standard services. Supabase Auth, Firebase Auth or Clerk for logins, Stripe Checkout for payments. These are well documented, so bugs around them are usually quick to find.
  • The bugs are local. One page or one flow is broken, not everything at once.
  • It runs outside the builder. A developer can copy the code from GitHub, install it, build it and run it on their own machine.

If most of these are true, fixing is almost always cheaper. The screens, the texts and the flows you spent weeks on are worth keeping.

Signs a rebuild is cheaper

  • Access to data is wrong at the root. The database has no access rules and the app only works because of that, or the rules about who may see what are checked only in the browser. Adding real rules later can break most pages at once. The 5 database checks show how to test this.
  • The data model fights your business. Everything sits in one big table or in loose JSON fields, the same data is stored in three places, and every change touches every page.
  • The same feature exists several times. Files like Checkout.tsx, CheckoutNew.tsx and Checkout2.tsx, each from a different prompt round, and nobody is sure which one is live.
  • Your business changed. The app was built for one-off payments and you now sell subscriptions, or it was built for single users and now it's for teams. The old structure was right for an old plan.

The middle road: keep the screens, rebuild what's underneath

Often the best answer sits in between. AI builders are good at screens: layouts, forms, buttons, the parts your users see. They struggle more with the parts nobody sees: who may read which data, what happens after a payment, and what runs on the server instead of in the browser.

So the cheapest path is often to keep the screens and rebuild the data model, the access rules and the payment handling underneath them, one flow at a time. Your users see the same app. It just stops breaking.

Once it's stable, the launch-ready checklist covers what to check before real users pay.

A 30-minute self-check

  1. Code out. Is the code in a GitHub account you own? If not, connect it now.
  2. Secret keys. Open your live site in Chrome, open DevTools, press Ctrl+Shift+F (Cmd+Option+F on a Mac) to search all files, and search for sk_live (a Stripe secret key) and sb_secret (a Supabase secret key). Neither may ever show up in the browser. On older Supabase projects, check that the key in the browser is the one marked anon or publishable in your API settings, never service_role.
  3. Tables. Open your database dashboard and write one sentence per table. Note the ones you can't explain.
  4. Money flows. Write down the 3 to 5 flows that make or keep money: sign up, pay, use the main feature, cancel. Run each one on your phone and mark the ones that break.
  5. Duplicates. Scan the file list in GitHub for near-identical names ending in New, 2, Old or Fixed.

Reading the result

  • A secret key in the browser is an emergency, not a reason to rebuild. Replace the key today in the Stripe or Supabase dashboard, then move the code that uses it to the server.
  • You can explain your tables and only one or two flows break: it's a fix.
  • The tables make no sense, most flows break and duplicates are everywhere: get a second opinion on rebuilding what's underneath before you write the next prompt.
