Your app lets people sign up. It has no "delete my account" button, or the button only hides the profile. Then Apple rejects the build, Google Play flags the listing, or a user emails you and asks you to erase their data. It is easy to miss in apps built with Lovable, Bolt, Cursor or Replit: sign-up gets built first, and the way out often never does. Vendor and legal facts below come from the official pages, checked in November 2026. This is not legal advice.

Short answer: Deleting an account means deleting the person everywhere their data lives. That is the login, their rows in your tables, their files, and the copies in other services such as Stripe or your email tool. Apple and Google both require an in-app way to start it. Google also wants a web link. Most of the work is on the server, because the delete call needs a secret key that must never be in the browser. Hiding the profile or "deactivating" the account is not enough.

1. Who requires it

Apple

App Review Guideline 5.1.1(v) says: "If your app supports account creation, you must also offer account deletion within the app." Apple's page Offering account deletion in your app adds the details:

  • "Offer to delete the entire account record, along with associated personal data."
  • "Only offering to temporarily deactivate or disable an account is insufficient."
  • You may ask the user to confirm, but "apps that make it unnecessarily difficult for someone to delete their account will not pass review."
  • If the user has an auto-renewable subscription through Apple, tell them that billing continues through Apple and ask them to cancel first.

Google Play

Google's account deletion requirement says that if users can create an account in your app, you must "provide users with an in-app path to delete their app accounts and associated data." You must also "provide a web link resource where users can request app account deletion and associated data deletion." The web link matters for people who already uninstalled the app. It should not make them download it again.

The same page says data you share with service providers should also be removed, and you should ask those providers to do the same. It also allows you to keep some data for reasons such as security, fraud prevention or regulatory compliance. If you do, "you must clearly inform users about your data retention practices," for example in your privacy policy.

GDPR

If you have users in the EU, they have a right to erasure. Article 17 starts: "The data subject shall have the right to obtain from the controller the erasure of personal data concerning him or her". In plain words: a person can ask you to delete their personal data, and in many cases you must. There are exceptions, so check your own situation. See also the GDPR checklist for a small app.

2. What "delete" must cover

Make a list of every place a user's data lives. For a typical AI-built app it looks like this:

  • The auth user. The login record itself.
  • Rows in your tables. Profiles, posts, orders, settings, messages. Anything with a user id.
  • Files in storage. Avatars, uploads, documents.
  • Copies in other services. The Stripe customer, your email list provider, analytics, error tracking, support tools.

Some data you may need to keep, for example invoices you need for your accounting. Whether and how long you must keep something depends on your country and your business. Check your own legal duties, and ask an accountant or lawyer. Whatever you keep, say so in your privacy policy, and keep only what you need.

Ask your AI tool to find the list for you. It often misses tables that were added later, so check the result against your database.

3. Supabase

The login needs the admin API

The deleteUser reference says: "Delete a user. Requires a service_role key." It also warns: "This function should only be called on a server. Never expose your service_role key in the browser."

So the "Delete account" button must call a server function (for example an Edge Function). That function checks who is logged in, then deletes that user and nobody else. Never take the user id from the request body without checking it against the logged-in session. If your service role key is in front-end code, fix that first. See the API key check.

The same reference has a shouldSoftDelete option. It is off by default. The page says a soft-deleted user can still be identified through a hashed user ID. For a real erasure, leave it off.

Your tables: cascade or clean up

Supabase's page on managing user data says to reference the auth.users table to keep data safe: "Specify on delete cascade in the reference." With that, deleting the auth user deletes the linked rows. Tables made by an AI tool often miss this. Ask your tool to check every table that has a user id. If a table cannot cascade, delete its rows in your server function before you delete the user.

Storage files are a trap

The same page warns: "You cannot delete a user if they are the owner of any objects in Supabase Storage." It says you get an error when you try to delete such a user. The fix it gives is to delete that user's storage objects, or give them to another user. So the order matters: remove the files first, then the user. The docs page does not say that files are deleted for you, so plan to delete them yourself.

The session may live on

The page also notes that deleting a user "does not automatically sign out a user." An access token that was already issued stays valid until it expires. Deleting through auth.admin.deleteUser() removes the user's sessions and invalidates the refresh tokens, so no new access tokens can be issued. Sign the person out in the app after the delete anyway.

4. Firebase

The login

Firebase's manage users page says: "You can delete a user account with the delete method." There is a catch: "To delete a user, the user must have signed in recently." Deleting an account is one of the security-sensitive actions. If the sign-in is too old, "the action fails with an error." The fix is to ask the user for their password or sign-in again, call reauthenticateWithCredential, then retry. You can also delete a user from the server with the Admin SDK.

Firestore and Storage are separate

Deleting the Auth user does not remove the user's Firestore documents or Storage files. They are separate products. You delete them yourself, in a server function, or with the Firebase extension Delete User Data. Its description: "Deletes data keyed on a userId from Cloud Firestore, Realtime Database, or Cloud Storage when a user deletes their account." It only deletes the paths you set up for it. So you still need the list from section 2, and you must keep it up to date when you add new tables.

5. Stripe

If the user ever paid, there is a Stripe customer. The delete customer reference says it "permanently deletes a customer. It cannot be undone. Also immediately cancels any active subscriptions on the customer." It also says deleting a customer "removes all credit card details and prevents any further operations."

Two things follow. First, think about the order. If you delete the customer by mistake while someone still has an active plan, the plan is gone at once. Decide whether you want to cancel at the end of the period first. On Apple, subscriptions bought in the iOS app are billed by Apple, so follow Apple's note from section 1.

Second, you may need payment records for your books. Stripe keeps its own records. Check your own legal duties before you decide what to remove from your side.

6. Backups

Deleted data can still exist in backups until those backups expire. That is normal, but you should know it. Find out how long your backups are kept, and write it in your privacy policy in plain words. Do not restore an old backup without deleting the people who asked to be erased since. See database backups for Supabase, Neon and Firebase.

7. The flow users see

  1. A clear button. Put "Delete account" in the account settings, where people look for it. Apple says to make it easy to find.
  2. A confirmation step. Say what will be removed, and that it cannot be undone. One extra step is fine. A maze is not.
  3. A re-login if needed. Ask for the password or send a sign-in code. This also stops someone with a stolen open session from deleting the account. See hardening login in an AI-built app.
  4. The delete itself. Run on the server. Files first, then rows, then third-party copies, then the login.
  5. An email that confirms it. Send it to the address on the account. Say what was deleted and what you keep, if anything.

You also need a way for people without the app, for Google Play and for GDPR requests. A simple web page works: the user signs in and deletes, or sends a request from the email on the account. Put the link in your Play listing and your privacy policy. Apple says not to make app users go through email or chat, so the in-app button must work by itself. Email is a fallback for those who cannot sign in.

When someone emails you, do not delete on the word of an unknown sender. Reply to the address on the account, or ask them to confirm from it. Then run the same deletion you built for the button, so there is one process, not two.

8. Prompts for your AI tool

  • "List every table, storage bucket and third-party service that holds data linked to a user id. Show how each one is deleted today."
  • "Add a server function that deletes the current logged-in user. It must read the user id from the session, never from the request. Use the service role key only on the server."
  • "Check every foreign key to the users table. Add on delete cascade where it is safe, and tell me where it is not."
  • "In the delete function, remove the user's storage files first, then the rows, then the Stripe customer, then the auth user. Return a clear error if a step fails."
  • "Add a Delete account button in settings with a confirm step and a recent sign-in check. After success, sign out and send a confirmation email."

Then test it with a throwaway account that has data in every table, a file and a test-mode payment. Check each place by hand afterward.

9. Checklist

  • A Delete account button exists in the app, not only a deactivate option.
  • There is a confirm step and a recent sign-in check.
  • Deletion runs on the server and checks who is logged in.
  • The service role key is not in the browser.
  • Auth user, table rows and storage files are all removed.
  • Supabase: files are removed before the user, and foreign keys cascade.
  • Firebase: Firestore and Storage data are deleted too, by code or by the extension.
  • The Stripe customer and other third-party copies are handled.
  • You know what you must keep, and your privacy policy says so.
  • Backup retention is known and written down.
  • A web page or link exists for deletion requests, for Google Play.
  • A confirmation email goes out.
  • Tested with a throwaway account and checked in every place.
