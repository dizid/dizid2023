Short answer: Bills grow when traffic, data or compute grows, and a bug or a bot can make any of them grow fast. Some tools can really stop usage: Vercel (if you switch on pausing), Supabase (on the Pro plan, for some items), Netlify (a hard limit on the Free plan) and Firebase (the no-cost Spark plan). Google Cloud budget alerts, which cover Firebase on the Blaze plan, only warn. Set the limits that exist, add alerts where they do not, send the alerts to an inbox you read, and look at the usage page once a month. 1. What makes a bill grow

The names differ per vendor. The pattern is the same: you pay for what is used, and "used" can be driven by visitors, by bots or by your own code. I describe only what each vendor's docs say. I give no prices, because prices change. Check the vendor's pricing page for current numbers.

Vercel

Vercel's page on how usage is calculated walks through a visit to a site. Each step uses priced resources. CDN requests are "charged per network request to the CDN". Fast Data Transfer is "charged based on data moved to the user from the CDN". A Vercel Function adds charges "for activating a function" and for the CPU time it uses. So more page views, more data sent and more function calls all raise the bill. The same page says the details depend on your framework and code.

Netlify

Netlify's credit-based plans use monthly credits. The page lists what uses credits: function compute (measured in GB-hours), web requests (which "includes edge functions"), web bandwidth, database compute and bandwidth, and production deploys. The docs do not make clear how build minutes are billed, so I leave that out.

Supabase

Supabase's egress page says: "You are charged for the network data transmitted out of the system to a connected client." That covers Database, Auth, Storage, Edge Functions and Realtime. So a large query result or a big file sent to every visitor counts. The cost control page also lists other usage items such as disk size, storage size, edge function invocations and monthly active users.

Firebase

Firestore's pricing page says you pay for "the number of documents you read, write, and delete", the index entries read for a query, storage, and network bandwidth. Some details matter for AI-built apps. A query is charged for the documents it reads. With a real-time listener, "you are charged for a read each time a document in the result set is added or updated". With an offset, "you are charged a read for each skipped document". So the shape of your queries decides your bill, not only the number of users.

2. What can stop spending and what only warns

This is the part most people get wrong. An alert tells you. A cap stops usage. Not every service has a cap, and some caps have gaps.

Vercel Spend Management: can stop, if you switch it on

Vercel's Spend Management is available on Pro and on Enterprise teams on the Flexible Commitment plan. The key warning in the docs: "Setting a spend amount does not stop usage on its own." To stop costs you must turn on Pause Production Deployments. Then Vercel pauses the production deployment for all projects when the amount is reached. While paused, "your websites, APIs, and functions are unavailable to visitors until you resume each project". Visitors see a 503 error.

Things to know from the same page:

  • Alerts by web and email come at 50%, 75% and 100% of your amount. SMS is available at 100%.
  • Checks run every few minutes, so pausing "can trigger several minutes after you cross your spend amount". The docs suggest setting the amount below the maximum you would accept.
  • Projects do not unpause by themselves. You resume each one by hand.
  • Stored resources are not deleted, so storage charges continue.
  • Seats and add-ons are not part of the spend amount.

Netlify: a hard limit on Free, credits on paid plans

On Netlify's credit-based plans, the page lists the Free plan as "300 credits/month with credit hard limit" and says there is no recharge option. The how credits work page explains the result: "Once your credit balance is completely used up, all of your web projects (sites/apps) are paused and visitors to your web projects will find a Site not available page". On paid plans you can buy more credits or turn on auto recharge, which the same page says keeps your web projects active. So on a paid plan, the choice is between a paused site and a larger bill. Decide which you prefer, and set it on purpose. This describes credit-based plans only. If your account is on an older plan, read your own billing page.

Supabase Spend Cap: stops some items, not all

The Spend Cap "is available only with the Pro Plan". It "determines whether your organization can exceed your subscription plan's quota for any usage item". When it is on and a covered item hits its quota, "further usage of that item is disallowed until the next billing cycle". But "only certain usage items are covered". Covered items include egress, disk size, edge function invocations, monthly active users, realtime messages and storage size. Items that are "predictable and explicitly opted into by the user" are excluded, with compute as an example. The docs also mention that services may be restricted under their Fair Use Policy. You set it in the Cost Control section of the organization billing page.

Note the trade-off: a cap protects your wallet, but a covered service can stop working for your users until the next cycle.

Firebase: Spark stops, Blaze only warns

Firebase's pricing plans page says that on the no-cost Spark plan, when you pass a limit, "your project's usage of that specific product will be shut off for the remainder of that month". On the pay-as-you-go Blaze plan there is no general cap. Google's budget documentation is clear: "Setting an alerts-only budget doesn't automatically cap Google Cloud or Google Maps Platform usage or spending." Budget alerts "do not cap your usage or charges", as the Firebase page puts it too.

Details from the budget page: default thresholds are 50%, 90% and 100% of the budget. Email goes to billing admins and users on the account by default. There is also "a delay between your use of Google Cloud resources, and the usage costs reporting to Cloud Billing". So set the budget lower than what you can afford.

For some Firebase products (Cloud Functions for Firebase and App Hosting, for example) the Firebase page recommends spend caps, which "will pause any new usage of the applicable service if your project reaches the budget set for that service". The page also mentions that budget notifications can be used to switch off billing on a project by code. That is extra work, so ask a developer to set it up and test it.

3. Common causes in AI-built apps

AI tools write code that works on a test with one user. A bill spike often comes from a pattern that looks fine until real traffic arrives. These are general patterns, not numbers.

  • A loop on every render. A component calls the API or database each time it draws. One page view turns into dozens of calls. On Firestore, that means many reads. On Supabase, more data out.
  • Polling every second. A page asks "anything new?" again and again, even in a background tab, even with no new data. On Firestore, each change in a result set costs reads, so keep the queries small.
  • No pagination. The app loads the whole table or collection and shows a few rows. You pay for all of it, every time.
  • Crawlers and bots on function routes. Bots hit your function URLs and forms. Each hit is a function call. See how to stop fake bot signups.
  • Large images served straight from storage. A large photo shown as a small thumbnail still sends the whole large file. Resize and compress files, and use a CDN or cache where your platform offers it.

These problems also make an app slow, so fixing them helps users too. See why AI-built apps are slow and how to fix them.

4. The 15-minute setup

  1. Write down your stack. Which host (Vercel or Netlify) and which database (Supabase or Firebase)? Find out which plan each account is on. Plan decides which controls exist. (2 minutes)
  2. Use an inbox you read. Make sure the billing contact on every account is an email you check daily, not an old address or a builder's default. (2 minutes)
  3. Vercel: open Settings, then Billing, and turn on Spend Management. Set the On-Demand Budget. Decide on Pause Production Deployments. Check that your own notifications are on in My Notifications. (3 minutes)
  4. Netlify: open your billing and credit pages. Know your plan's limit. Decide on auto recharge: off means a paused site is the worst case, on means a bigger bill is. (2 minutes)
  5. Supabase: if you are on Pro, open the organization billing page, find Cost Control and check that the Spend Cap is the way you want it. Remember compute is not covered. (2 minutes)
  6. Firebase or Google Cloud: if you are on Blaze, create a budget in Cloud Billing with alerts. Set the amount below what you can afford, because alerts arrive with a delay. Remember it will not stop anything. (3 minutes)
  7. Put a monthly reminder in your calendar. Open the usage page of each service and look at the graphs. Supabase's usage page shows egress by service per day. (1 minute to set up)

5. If a bill already spiked

  1. Look at the usage breakdown first. Which item jumped: bandwidth, function calls, database reads, storage? And on which day? The day often matches a deploy or a post that went viral.
  2. Find the route or function. Check logs for the URL or function with the most calls. Look at who calls it: real users, one IP range or bots.
  3. Stop the leak. Roll back to the last good deploy, pause the project or disable the function. Turn on the cap or limit if it was off. A short outage is cheaper than a long spike.
  4. Fix the cause. Add pagination, remove the polling, cache the response, resize the images, block the bots. Then watch the usage for a few days.
  5. Contact support. Send the dates, the usage graph and what you changed. Be polite and factual. Support decides what they do. Do not count on a refund.

6. Checklist

  • I know my host, my database and the plan of each.
  • Billing emails go to an inbox I read.
  • Vercel: Spend Management is on, and I chose whether to pause production.
  • Netlify: I know what happens at the credit limit and chose my auto recharge setting.
  • Supabase: the Spend Cap is set as I want, and I know compute is outside it.
  • Firebase: Spark, or a Blaze budget with alerts below my real limit.
  • I know which tools only warn and which really stop usage.
  • I check the usage pages once a month.
  • No loop or polling calls the API or database more than needed.
  • Lists are paginated and images are resized.
